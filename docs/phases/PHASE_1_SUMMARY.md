# Phase 1 — Foundation: summary

Requirements: OPS-01, OPS-02, API-01.

## What was built
- `pyproject.toml`: uv project (Python 3.12), ruff + mypy (strict) + pytest config.
- `src/spotwise/config.py`: `Settings` (pydantic-settings) reads `.env`. Secrets are `SecretStr`, so they never show up in logs or `repr`.
- `src/spotwise/db/models.py`: SQLAlchemy 2 typed models for `prices`, `ingestion_runs` and `quality_results` (schema from the brief, section 7).
- `migrations/versions/0001_initial_schema.py`: first Alembic migration, including the `prices_hourly` view.
- `src/spotwise/api/`: FastAPI app with `GET /health` (200 if the DB answers `SELECT 1`, 503 if not).
- `docker-compose.yml`: Postgres 16 with a named volume. `Makefile`: common commands.
- `.github/workflows/ci.yml`: ruff, mypy, migrations and pytest against a Postgres service container.

## Decisions (and why)
- **Sync SQLAlchemy + psycopg 3**, not async. It's simpler to read and debug, and our load is tiny.
- **Migration written by hand**, not autogenerated, so it matches the brief exactly (UNIQUE on `area, ts_start, resolution_minutes`; CHECK on resolution 15/60).
- **`prices_hourly` view**: if an hour has 15-minute rows, it averages them and ignores any hourly row for that hour. Hours are truncated in UTC, which is safe because Helsinki's offset is a whole number of hours.
- **`env_ignore_empty=True`**: blank lines like `LLM_MODEL=` in `.env` fall back to defaults instead of crashing.
- **`/health` uses a dependency (`get_db_check`)**, so unit tests can fake the DB being up or down.
- **ruff rule `DTZ`** blocks naive datetimes; **`T20`** blocks `print` in app code (CLAUDE.md rules).
- **DB tests are marked `db`** and skip automatically when Postgres isn't running, so `uv run pytest` still works on a laptop without Docker. CI always runs them.

## Verified
- `ruff check`, `ruff format --check`, `mypy`: clean.
- Against a real Postgres 16: `alembic upgrade head` → `downgrade base` → `upgrade head` works; 11/11 tests pass; `/health` returns `{"status":"ok","db":"ok"}`.

## Learn this (interview)
- **Alembic**: version control for the DB schema. Each migration has an `upgrade` and a `downgrade`, and the `alembic_version` table records which one is applied.
- **pydantic-settings**: one typed, validated place for configuration. The app fails at startup on bad config, not halfway through a run.
- **Postgres service container in CI**: CI tests against the same database engine as production, so the migrations and the UNIQUE constraint are really tested.
